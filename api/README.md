# api/ — каркас под Node.js-бэкенд

Пока пусто: фронтенд работает на моках. Здесь описано, куда всё встанет,
чтобы переход был механическим, а не переписыванием.

## Как фронт получает данные сейчас

Все запросы идут через **`src/lib/api.js`** — компоненты никогда не
импортируют `src/data/*` напрямую. Функции уже возвращают `Promise`
с искусственной задержкой, поэтому состояния загрузки и ошибок написаны
и протестированы заранее.

## Что делать, когда появится бэкенд

1. Поднять сервер здесь (Express / Fastify) по контракту из [`CONTRACT.md`](./CONTRACT.md).
2. В `src/lib/api.js` заменить тела функций на `fetch`. Сигнатуры не менять.
3. Удалить `src/data/*.js`.
4. Добавить в `vite.config.js` прокси, чтобы в разработке не ловить CORS:

```js
server: {
  port: 5173,
  proxy: { '/api': { target: 'http://localhost:3000', changeOrigin: true } },
}
```

Ни один компонент при этом не трогается.

## Предполагаемая структура

```
api/
├── src/
│   ├── index.js          # точка входа, поднимает сервер
│   ├── routes/           # dolls.js, builds.js, gallery.js, faq.js
│   ├── controllers/      # логика, отдельно от роутов
│   ├── db/               # схема и подключение
│   └── middleware/       # валидация, ошибки, rate limit
├── package.json
└── .env.example
```

## О чём подумать заранее

- **Загрузка фотографий.** Кукол снимают с двух сторон, как у Coco Violet.
  Нужно хранилище и ресайз — иначе страница каталога потянет мегабайты.
- **Штучность товара.** Кукла существует в одном экземпляре: нужна
  блокировка, чтобы двое не купили одну и ту же. Проверка «в наличии»
  на клиенте не считается.
- **Заявки из конструктора.** `POST /api/builds` сохраняет конфигурацию
  и шлёт письмо. Конфигурация уже сериализуется в URL — тот же формат
  можно писать в базу как есть.
